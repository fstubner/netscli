# Winget (microsoft/winget-pkgs)

## Submission flow

Unlike Homebrew or Scoop (which use taps/buckets you control), Winget
packages are all submitted to the central
[microsoft/winget-pkgs](https://github.com/microsoft/winget-pkgs)
repo via PR.

Users install with:

```powershell
winget install netscli           # resolves via moniker
# or
winget install fstubner.netscli  # canonical package id
```

The CLI package is **portable**. The release asset is a single
`netscli-windows-x86_64.exe`, not an installer EXE. Its initial Winget
manifest must therefore use:

```yaml
InstallerType: portable
Commands:
  - netscli
```

The checked-in reference manifests under `cli/<version>/` capture that
shape. The automated `winget-releaser` update should preserve the
accepted manifest's installer type once the first CLI package is in
`microsoft/winget-pkgs`.

## What the checked-in directories are

Verbatim copies of manifests that are live in `microsoft/winget-pkgs`,
fetched from the catalog rather than written here — `cli/v0.2.6/` and
`gui/0.2.6/` are byte-identical to what the catalog serves. That is the
only thing they are good for: showing the shape a real accepted manifest
has, so a future submission can be compared against one.

Three directories that were not that have been removed. `cli/0.3.0/` and
`gui/0.3.0/` described a version that was never released — the v0.3.0 tag
was deleted before it shipped — and `gui/0.2.4/` was a submission a
moderator rejected, so no such manifest exists in the catalog either. All
three were hand-written to a shape the pipeline does not actually produce:
`ManifestVersion 1.9.0` with `InstallerType` nested under `Installers:`,
where `winget-releaser` (via komac) emits `1.12.0` with `InstallerType`
and `Commands` at the document root. A reference copy that does not match
what the tool generates is worse than no reference copy, because the whole
point is comparing a generated PR against it.

The CLI directory is named `v0.2.6`, with the `v`, because that is its
name in the catalog. Five CLI versions were published carrying a leading
`v` in `PackageVersion`; see the "PackageVersion carries no `v`" section
of [`docs/PUBLISHING.md`](../../docs/PUBLISHING.md) for how that happened,
why it does not break upgrades, and why removing them is optional.

## Tooling: wingetcreate

Microsoft provides a CLI (`wingetcreate`) that generates the three
required YAML manifest files (`.installer.yaml`, `.locale.en-US.yaml`,
and the root version manifest) from a release URL:

```powershell
winget install Microsoft.WingetCreate

wingetcreate new `
  --urls https://github.com/fstubner/netscli/releases/download/vX.Y.Z/netscli-windows-x86_64.exe `
  --version X.Y.Z `
  fstubner.netscli
```

This pops an editor with the three YAML files. Verify:
- `PackageIdentifier: fstubner.netscli`
- `Moniker: netscli`
- `InstallerType: portable`
- `Commands: [netscli]`
- `InstallerSha256` — compare against the `.sha256` on the release
- `License: MIT`
- `Homepage: https://netscli.com`
- `ShortDescription: Network diagnostics CLI, terminal UI, and MCP server`

Then:

```powershell
wingetcreate submit --token <gh-token> manifests/f/fstubner/netscli/X.Y.Z
```

This forks microsoft/winget-pkgs, pushes the manifests, and opens the PR
automatically.

## After each release

Re-run `wingetcreate update`:

```powershell
wingetcreate update fstubner.netscli `
  --urls https://github.com/fstubner/netscli/releases/download/vX.Y.Z/netscli-windows-x86_64.exe `
  --version X.Y.Z `
  --submit --token <gh-token>
```

This auto-opens a follow-up PR updating the existing manifest.

## Reference manifest (what wingetcreate generates)

The YAML generated by `wingetcreate` lives at
`manifests/f/fstubner/netscli/<version>/` in the winget-pkgs repo.
Nothing here is read by the pipeline, so committing a copy is optional.
If you do, copy it out of the catalog once the submission is **accepted**,
unedited — see "What the checked-in directories are" above for why a
hand-adjusted or speculative copy is worse than none.
